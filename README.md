# TP3 - Gestion des réservations

A small Java project that models room bookings with JPA/Hibernate on an in-memory H2 database. Its focus is the relationships between entities: one-to-many, many-to-one, many-to-many, cascading operations and orphan removal.

## Technologies

- Java (8 or newer)
- Maven
- Hibernate Core 5.4.30.Final (JPA 2.2 implementation)
- JPA API 2.2 (`javax.persistence`)
- H2 Database 1.4.200 (in-memory, runtime scope)

## Data model

| Entity | Fields |
|---|---|
| `Utilisateur` | `id`, `email` (required, unique), `nom` (required) |
| `Salle` | `id`, `nom` (required), `capacite` (required) |
| `Equipement` | `id`, `nom` (required, unique) |
| `Reservation` | `id`, `debut` (required), `fin` (required) |

All identifiers are generated by the database (`GenerationType.IDENTITY`).

### Relationships

```
Utilisateur 1 ────< Reservation >──── 1 Salle
                                         │
                                         └──< >── Equipement   (many-to-many)
```

| Relationship | Owning side | Details |
|---|---|---|
| `Utilisateur` one-to-many `Reservation` | `Reservation.utilisateur` | `cascade = ALL`, `orphanRemoval = true` |
| `Salle` one-to-many `Reservation` | `Reservation.salle` | `cascade = ALL`, `orphanRemoval = true` |
| `Salle` many-to-many `Equipement` | `Salle.equipements` | Join table `salle_equipement` (`salle_id`, `equipement_id`); `Equipement.salles` is the inverse side |

`Reservation` holds the foreign keys `utilisateur_id` and `salle_id`, both required.

The helper methods `Utilisateur.addReservation` / `removeReservation` and `Salle.addEquipement` / `removeEquipement` keep both sides of a relationship in sync.

### Validation

A `Reservation` checks its dates before every insert and update (`@PrePersist` and `@PreUpdate`). It throws an `IllegalArgumentException` if a date is missing or if the start is not strictly before the end.

## What the demo does

`App.main` creates the `EntityManagerFactory` for the unit `gestion-reservations-pu`, then in one transaction:

1. Creates a user (Alice Dupont) and a room ("Salle A")
2. Creates a piece of equipment ("Projecteur") and adds it to the room
3. Creates a reservation linking the room and the user, and adds it to the user
4. Persists the user, relying on the cascade to reach the reservation

## Configuration

The persistence unit is defined in `src/main/resources/META-INF/persistence.xml`:

- H2 in-memory database `jdbc:h2:mem:test`, user `sa`, empty password
- `hibernate.hbm2ddl.auto=update`: tables are created or updated at startup
- `hibernate.show_sql=true` and `hibernate.format_sql=true`: generated SQL is printed in the console
- The four entity classes are listed explicitly

The database lives in memory, so all data is lost when the program ends.

## Notes

- **Cascade on rooms:** `Reservation.salle` has no cascade, so persisting a user does not persist a room that is not already saved. Persist the room first (`em.persist(salle)`) or add `cascade = CascadeType.PERSIST` to `Reservation.salle`.
- **Tests:** `AppTest.java` uses JUnit, which is not declared in `pom.xml`. Add the `junit` dependency (test scope) before running `mvn test` or `mvn package`.
- **Java version:** `pom.xml` does not set a compiler level. Add `maven.compiler.source` and `maven.compiler.target` to `<properties>` to be sure it builds on every Maven setup.
- **Duplicate annotation:** `Equipement` declares `@ManyToMany(mappedBy = "equipements")` on both the field and the `getSalles()` getter. Only the field one is used, since the entity uses field access, so the one on the getter can be removed.
